# ISUCON14(ISURIDE): ユーザーストーリーと加点動作

最終更新日: 2026-10-12 / 対象: https://isuride.xiv.isucon.net/(練習環境 i1)/ 確認済み経路: 3 本 / 今回の追加: US-01〜US-03

> `isucon-user-stories` スキルの成果物です。**このファイルが唯一の累積レポートです。** 追加で調査するときはこのファイルを更新し、レポートを増やさないでください。
> 事実は `logs/` の操作ログにあり、ここにはその解釈を書きます。根拠は事実 ID で示します。
> **ブラウザでの手動の成功は、ベンチのスコアの増分ではありません。** ここでは採点式に当てて、「同種の成功が計上されれば何点相当」と条件付きで書くにとどめます。

**アプリの概要**: ISURIDE は椅子の配車サービスで、次の3つの画面があります。

- 利用者のクライアント(`/client`): 乗車位置と目的地を選んで配車を要求し、到着したら評価して支払います。
- オーナーの管理画面(`/owner`): 自分の椅子の一覧と売上を見ます。
- 椅子の動き: 実環境ではベンチ、ブラウザでは `/simulator` が担当します。`POST /api/chair/coordinate` と `POST /api/chair/rides/{ride_id}/status` でライドを進めます。

利用者のライドが終わると、その運賃がオーナーの売上に計上されます。

## 1. 仕様と採点

出典は `docs/manual.md` と `docs/ISURIDE.md` です。

- **採点式**(manual.md「スコアの計算」362〜367行): 次の合計です。
  - 「椅子がライドとマッチした位置から乗車位置までの移動距離の合計 × 0.1」
  - 「椅子の乗車位置から目的地までの移動距離の合計」
  - 「ライド完了数 × 5」
- **加点対象の動作**: ライドが完了すること(完了数)と、椅子が移動すること(マッチ位置から乗車位置まで、乗車位置から目的地まで)です。ISURIDE.md の状態遷移では、完了は「ARRIVED → COMPLETED: ユーザーがライドの評価を完了する」です。
- **減点・失格条件**: 減点の項目はありません。負荷走行は次の場合に FAIL として打ち切られます(manual.md「負荷走行の打ち切り」)。
  - 初期化か整合性チェックの失敗
  - クリティカルエラー(想定外の通知や状態遷移、長時間マッチングされないライド、ユーザーの評価のタイムアウト、「評価は完了しているが、支払いが行われていないライド」、「決済サーバーに誤った支払い」など)
  - ワーニングが 200 件以上
  - さらに、負荷終了の時点で進行中の決済は、終了後 5 秒以内に完了しなければ FAIL です。
- **ベンチが叩く範囲**(manual.md「負荷走行」「猶予時間」)
  - 初期化で `POST /api/initialize`、`POST /api/owner/owners`、`POST /api/chair/chairs`、`POST /api/app/users` を叩きます。
  - 負荷は 60 秒です。
  - 猶予時間の節で `GET /api/app/nearby-chairs`、`GET /api/owner/chairs`、`POST /api/app/rides` に触れているので、これらも叩きます。
  - 静的ファイルや HTML を叩くかどうかは、資料に記載がありません(未確認)。
- **ブラウザ操作とベンチ負荷の違い**
  - ブラウザでは、椅子の動きを `/simulator` が1秒ごとに擬似的に進めます(ISURIDE.md「シミュレーターの注意事項」)。ベンチでは、ベンチ自身が椅子として振る舞います。
  - 追試には「アプリフロントエンドにアクセスし、表示を確認します。構造がリファレンス実装と異なる、意図しないデータが表示されている場合、失格」とあります(manual.md「追試」)。そのため、章5のベースラインとの見比べが要ります。

### 3.1 加点地点の実装照合

- ★ `POST /api/app/rides/{ride_id}/evaluation`(`go/app_handlers.go:508`)
  - 状態が ARRIVED でなければ 400(`:544`)。
  - `rides.evaluation` を UPDATE し(`:551`)、ride_statuses に COMPLETED を INSERT します(`:567`)。
  - そのあと、`calculateDiscountedFare` で割引後の運賃を出し(`:593`)、`settings.payment_gateway_url` の決済サービスへ同じトランザクションの中で支払いを依頼します(`:603-608`)。決済が成功してから commit します。
  - **決済サービスへの HTTP 呼び出しがトランザクションの中にあります。** クリティカルエラー「評価は完了しているが、支払いが行われていないライド」と、「負荷終了後 5 秒以内に決済が完了すること」の条件に直結する箇所です。
  - 今回の2回は、どちらも決済モックに `決済完了 … amount=500` が届いていました(V06、V12)。
- ★ `POST /api/chair/coordinate`(`go/chair_handlers.go:97`)
  - chair_locations を INSERT します。
  - 座標が乗車位置に一致し、状態が ENROUTE なら PICKUP を、目的地に一致し、状態が CARRYING なら ARRIVED を INSERT します。
  - 移動距離の加点は、この API で送られた軌跡からベンチ側が数えていると考えられます(採点の集計方法は資料に記載がなく、未確認)。
- クーポンが確定するのは、評価のときではなく配車要求のとき(`appPostRides`、`go/app_handlers.go:367-411`)です。
  - 初回のライドは `CP_NEW2024` を優先し、それ以外は作成順で最も古い未使用クーポンを使います。
  - 観測でも、story02 は初回のライドで `CP_NEW2024` を使い、`INV_…` は残りました(V11)。マニュアルの「新規登録キャンペーンによるクーポンの方が優先して使用されます」と合っています。

### 6.1 性能調査へつなげる観点

経路から推論したもので、実測ではありません。`isucon-app-map` の章11 が読みます。

- **加点地点の手前で繰り返し叩かれるエンドポイント**
  - `GET /api/app/notification` と `GET /api/chair/notification`。リファレンスでは `retry_after_ms` 30ms のポーリングで、ブラウザ1タブ(クライアントとシミュレーター)だけでも約2分で 1000 件近くたまりました(A16)。
  - ISURIDE.md によれば SSE にしてもよく、状態変化から3秒以内の通知が条件です。
  - ベンチでも呼び出し回数が最大のエンドポイントになると見られます。キックオフ時の alp でも、`/api/chair/notification` 9,393 回、`/api/app/notification` 4,181 回が上位でした。
- **複数の US が通る分岐点**
  - `POST /api/app/rides`: クーポンを `FOR UPDATE` で確定し、未完了のライドを確認します。
  - `GET /api/internal/matching`: ランダムに1台を選び、椅子が空いているかを ride_statuses の集計で判定します。
  - `POST /api/chair/coordinate`: 毎秒呼ばれ、状態遷移を判定します。
- **加点地点の整合性**
  - 評価の API は、決済サービスへの同期呼び出しをトランザクションの中で行っています(章3.1)。決済のリトライでレイテンシが伸びると、評価のタイムアウトや「支払いが行われていないライド」のクリティカルエラーに直結します。
  - マッチングを速くすると、ライドの完了数とマッチ位置からの距離(×0.1)の両方が増えます。ISURIDE.md によれば、近い椅子や速い椅子を割り当てると評価が上がり、利用者が増えます。

**手動の成功2件は、実測のスコア増分ではありません。** 採点式に当てると次のとおりです。

- US-01: 完了 5 + 乗車位置から目的地まで 20 + マッチ位置から乗車位置まで 0×0.1 = 25 点相当。
- US-02: 5 + 20 + 20×0.1 = 27 点相当(椅子が最短経路で動いた場合)。

これは「ベンチで同種の成功が計上され、FAIL 条件に当たらなければ」という条件付きの値です。
